## 設置ファイルと公開時の手順

- 現行サイト（`E:\project-folder`）: `home.html` / `gallery.html` / `contact.html` / `analytics.js` の4ファイルをサイトのルートへアップロードする。CSS・画像・`.htaccess` の変更は不要。
- リニューアル版: `mockups/` の全9ページと `mockups/assets/analytics.js`。ローカルデモにも同期済み。本番移行時はこのスクリプトも含めて公開する。
- 測定ID・許可ホストを変更するときは `analytics.js` の設定を更新する。現行とリニューアルでは配置階層が違うが、スクリプトの内容は同じ。
- 変更前HTMLは `work/backups/20260906-031338-before-ga4-tags.zip` に保存。復元時は対応する現行／リニューアル用HTMLを戻せば新規タグは読み込まれない。
- 基本タグは1ページ内で1回だけ初期化し、通常のページ閲覧を計測する。別途同じGoogleタグをHTMLやGTMに重ねて追加しない。[Google公式の設置・検証手順](https://developers.google.com/tag-platform/gtagjs)

## 管理と導入時に確認する情報

- クライアントが管理する既存GA4があれば引き継ぎ、新規ならクライアント管理のアカウント・プロパティとして作成する。制作担当者には必要な権限を付与する。
- 測定ID `G-2VPT10TFBK` のGA4プロパティ・ウェブデータストリームとクライアントの管理者を確認する。パスワードの共有は不要。
- 本番サイトのホスト名と実際のShopifyチェックアウト先を確定する。現行サイトは `km-nagoya-doll.com`、制作プレビューは `hirojessica.github.io/kmrn/`。計測対象は実際の公開構成に合わせる。
- 本番とテストの計測を分ける。localhost・GitHub Pagesプレビュー・購入テストのデータを本番レポートへ混在させない。検証には別プロパティを使う。

## 現在の構成に合わせた実装方針

公開対象は `mockups/` の静的サイトで、商品情報をShopify Storefront APIから取得している。Shopifyテーマにだけタグを追加しても、このサイトの閲覧計測は完了しない。

静的サイトの9ページ（トップ・会社案内・商品一覧・商品詳細・お知らせ一覧・記事詳細・ギャラリー・お問い合わせ・送信後）に共通のGoogleタグを設置済み。既存GTMへ統合する場合は重複設置を避ける。

Shopify側は公式のGoogle & YouTubeチャネルによるGA4連携を基本案とする。GA4だけの設定にはMerchant Centerとの接続は不要。現在のHeadlessサイトからチェックアウトへ進む経路で対応状況を確認してから採用する。[Shopify公式のGA4設定手順](https://help.shopify.com/en/manual/reports-and-analytics/google-analytics/google-analytics-setup)

ドメインをまたぐ計測では、同じウェブデータストリームの測定IDを使い、本番サイトと実際のチェックアウト先を設定する。リダイレクトで連携情報が失われないこと、流入元とセッションが引き継がれることを実際の購入経路で確認する。設定だけで確認済みとは扱わない。[Google公式のクロスドメイン計測](https://support.google.com/analytics/answer/10071811?hl=ja)

## 計測対象と発火条件

| 対象 | イベント案 | 確認する条件 |
|---|---|---|
| 各ページ・流入元 | `page_view` | ページ表示ごとに1回。自動計測と手動計測を重複させない |
| 商品一覧からの遷移 | `select_item` | 商品カードの選択。トップのおすすめと一覧を区別する |
| 商品詳細 | `view_item` | API取得が成功し、実商品を表示した時点。商品ID・種類・価格・通貨を付ける |
| Shopifyへの購入導線 | `checkout_click`（独自） | 有効な購入リンクの操作。注文完了やカート追加として集計しない |
| チェックアウト開始 | `begin_checkout` | Shopify側の実際の開始イベントで計測する |
| 購入完了・売上 | `purchase` | Shopify側の注文完了。取引ID・商品・種類・数量・金額・通貨・送料・税を注文データと照合する |
| 問い合わせ送信完了 | `generate_lead` | 送信成功を確認できた場合だけ。下記のFormSubmit制約を解消してから実装する |

商品IDは言語を切り替えても同じ体系を使用し、Shopify側と統一する。表示言語（JA/EN）は別の項目として記録する。言語切り替えや非同期再描画による同一表示の二重計測を避ける。

`purchase` は静的サイト側から重ねて送らず、取引IDを使って再読み込み時の重複も確認する。イベント項目はGoogleの推奨仕様に合わせる。[Google公式のEC計測](https://developers.google.com/analytics/devguides/collection/ga4/ecommerce)

### お問い合わせの制約

現在の `assets/contact.js` はFormSubmitの外部送信画面へ遷移し、成功後に `contact-thanks.html` へ戻す構成。送信ボタンのクリックでは成功を判定できず、送信後ページは直接アクセスもできる。

実装時は、成功後の戻りと送信前の一時状態を照合する方法などを検討し、直接アクセス・再読み込み・CAPTCHA失敗を送信完了件数に含めない。この方法はメール到達の証明にはならないため、レポート上はフォーム送信完了として扱う。確実な成功判定が必要なら送信サービス側の成功応答を受け取れる構成に変更し、受信確認と併せて検証する。

フォームの氏名・メールアドレス・電話番号・問い合わせ本文、および注文へのアクセス用URLや認証情報をGA4に送信しない。URLとイベントの送信内容も検査する。プライバシー説明と同意設定は本番運用方針に合わせる。

## 引き渡し完了条件

- [ ] クライアントがGA4へログインし、対象プロパティの管理権限を確認できる。
- [ ] 本番ドメイン・測定ID・タイムゾーン・通貨・管理者を引き継ぎ記録に残す。
- [ ] JA/EN両方でページ・商品表示・商品導線をDebugViewで確認する。
- [ ] Shopifyへの移動で流入元・セッションが引き継がれ、イベントが二重送信されない。
- [ ] 購入テストで商品・数量・金額・送料・税・取引IDを照合する。テストは本番売上集計に入れない。
- [ ] 問い合わせの成功・失敗・直接アクセス・再読み込みを確認する。
- [ ] アクセス数・流入元・商品閲覧・売上・問い合わせ送信完了を確認する操作手順をクライアントへ渡す。
- [ ] 本番公開時の計測開始とレポート反映を確認し、確認日時を記録する。

ECの本番決済開始は別作業。現在のクライアント移行用ストアと購入ボタンの販売準備状態は、GA4要件の追加では変更しない。
